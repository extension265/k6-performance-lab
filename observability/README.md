# Observability

`npm run stack:up` starts Prometheus, Grafana and cAdvisor alongside the API. All three are pinned, resource-capped and bound to `127.0.0.1`.

| Service | URL | Purpose |
|---|---|---|
| Grafana 13.3.1 | http://localhost:3001 | Dashboards. Anyone can view without logging in; sign in as `admin` / `admin` to edit. |
| Prometheus v3.16.0 | http://localhost:9090 | Scrapes the API and cAdvisor every 5s, and receives k6 metrics by remote write |
| cAdvisor v0.60.6 | (internal) | Per-container CPU and memory, **including the k6 container** |

```
npm run test:load:prom        # any scenario + :prom pushes k6 metrics to Prometheus
npm run perf:fresh -- stress --prom
npm run dashboards:check      # verifies every panel on both dashboards returns data for the latest run
```

`dashboards:check` runs each panel's query through Grafana's datasource proxy. It substitutes the template variables itself, so it can't catch a variable that fails to resolve in the UI. That was the cause of the `quantile_stat` issue described below. After changing a dashboard, also open it, or take a screenshot of it.

Screenshots in `docs/images/` were taken with headless Microsoft Edge (`msedge --headless=new --screenshot`) against the `kiosk` view of each dashboard.

Every `--prom` run is tagged with a unique `testid` (`<timestamp>-<scenario>`). Both dashboards have a run picker that lists the newest run first.

## Dashboards (provisioned from `grafana/dashboards/`, nothing to click)

**API vs Load** is the home dashboard. It is generated by `grafana/build-api-vs-load.js`; run `npm run dashboards:build` after editing. Its rows share a crosshair, so hovering one panel shows the same moment in every other panel:

1. **Load generated (k6):** VUs, request rate, error rate (SLO line at 1%), checkout p95 (SLO line at 1.5s), and p95 per endpoint as k6 sees it.
2. **API (server side):** request rate, p95 by route, and 5xx responses (`503 db_pool_timeout` means the pool is exhausted).
3. **Database:**
   - pool in use, waiting and max;
   - p95 wait to get a connection from the pool;
   - which seeded bottlenecks are active;
   - query rate and p95 per named query. Under N+1, `payment_by_id` rises with every `GET /orders/:id`.
4. **Resources (cAdvisor):** CPU as a % of each container's limit (api, postgres, k6), and memory. The **k6 CPU gauge** shows the peak over the selected range. **Above 80%, the load generator is saturated and the run is invalid** (PLAN.md Phase 6).

**k6 Prometheus** is the official k6 dashboard, [grafana.com #19665](https://grafana.com/grafana/dashboards/19665) rev 3, published by Grafana k6. It has two local changes, both needed because the dashboard is provisioned from a file rather than imported through the UI:

1. The import-time `${DS_PROMETHEUS}` input is pointed at the provisioned datasource (uid `prometheus`), and `__inputs` is removed. File provisioning has no import step to fill that input in.
2. The "Trend Metrics Query" variable (`quantile_stat`) is now a fixed list: `p95, p99, avg, med, min, max`, default `p95`. These are exactly the stats `K6_PROMETHEUS_RW_TREND_STATS` exports. Upstream builds the list with `metrics(k6_http_req_duration_)` plus a regex. In Grafana 13.3 that returned nothing, which left every latency, duration and iteration panel showing "No data".

"HTTP request failures" shows "No data" when a run has zero failed requests. That is correct.

## k6 → Prometheus settings (`scripts/run-k6.js --prom`)

- Output: `experimental-prometheus-rw` (its name in k6 2.3.0), pushing to `http://prometheus:9090/api/v1/write` every 5s.
- `K6_PROMETHEUS_RW_TREND_STATS=p(95),p(99),min,max,avg,med`: the series the official dashboard expects (`k6_http_req_duration_p95`, …). Durations are in seconds.
- `K6_SYSTEM_TAGS` excludes `url`. Otherwise every order and payment id would create its own series. The `name` tag identifies endpoints.
